(catalog, plan/bind/approve, receipts, resource plane, honest no-answers, correction identity

## Findings

Blocking:
- F-4: `POST /v1/intelligence/builds/start` → 503 "no Intelligence build executor is registered
  for profile: intelligence_onboarding_profile:personal". Matches declared F5–F10 scope-out.
- F-5: No public mechanism to select/authorize a concrete local folder or file: prepare accepts
  only abstract source_group ids; recorded_source_selections remain empty through the whole chain;
  therefore the J3 promise (exact folder scope, access mode, expected contribution shown before
  any read) is unfalsifiable in 1.2.2.
- F-6: Shipped pack maps only `markdown.note`; PDF/CSV/JSON source kinds have no source mapping.

Non-blocking defects:
- F-1: `ace setup` (and every `ace service start`) ends with "Error: ACE started, but local-owner
  permission verification was incomplete." The API's bootstrap returns FIVE verified grants; the
  1.2.2 CLI hardcodes exactly FOUR (`setup.py::_bootstrap_local_owner`). False failure; it also
  poisons the product's own onboarding evidence (`ace onboarding report`: 0/2 setups successful,
  failure stage owner_authority).
- F-2: In a pip-only install, CLI settings load `.env` from the current working directory only;
  `ace doctor` run elsewhere silently uses default ws://localhost:8001 and can PASS against a
  different installation's database (it did, on this host, until rerun from
  `$ACE_CONFIG_DIR/runtime/`). Wrong-database readiness PASS is a trust defect.
- F-7: Resource-plane 409 for future timestamps says "could not preserve its exact contract"
  instead of naming the clock problem (the bind-step equivalent message is exact).
- F-8: Sentinel briefing written under `product:default` while the issued token scopes
  `product:platform`; briefing listing by the token's product returns empty.
- F-3 (minor): Catalog contains only Personal Intelligence — "beside the existing catalog
  entries" has no other entries to stand beside; Code Intelligence is a separate API family.

Documentation gaps:
- Doc-1: getting-started's adapter install command omits `ace_reference_workspace_action` even
  though the release notes include it in the bundle set.
- Doc-2: No documented way to relocate ACE state from `~/.ace` (ACE_CONFIG_DIR was discovered by
  reading installed package source); compose/port isolation vars are documented only inside the
  shipped `.env.example`. On a machine with any other ACE installation, following the docs
  verbatim would have collided with it.
- Transient: PyPI CDN lag (~6 min post-publish) made `ace-core==1.2.2` initially unresolvable;
  `--refresh` fixed it.

## Interventions / deviations (all recorded in RUN_LOG.md)
- Exercised Atrium's same-origin API rather than the browser UI (no browser in this environment);
  verified `ace atrium` serves the SPA.
- Isolation env vars exported before setup (ACE_CONFIG_DIR / COMPOSE_PROJECT_NAME /
  ACE_SURREAL_HOST_PORT=18122 / ACE_API_PORT=13122) to honor workspace confinement on a host with
  other ACE instances; one accidental read-only 401 against the default config when a CLI call
  omitted ACE_CONFIG_DIR.
- Composed bind/approve/start payloads by hand from OpenAPI + shipped bundle.json (no documented
  user-facing flow exists for these steps outside the unshipped Atrium journey).
- J8 exercised negatively (refusal of nonexistent claim identities) since no real claims existed.
